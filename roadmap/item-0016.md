Deferred follow-on from ADR-046 D9: machine-enforce the layer direction rather than rely on the file boundary plus review. The original base-/api-/wire- filename-prefix basis is dead -- the spec-layering reorg produced per-package tiers (primitive, concept, foundation/transport), not prefixed files within one package -- so the lint keys on the current package and tier layout instead. The Go side already enforces its layering via go-arch-lint; this is the mandatory CUE-side counterpart in the build gate. Whether the rule is a custom lint (tools/lintfrom mold) or an off-the-shelf CUE linter, and the exact classification predicate, are settled at authoring against the landed tier structure. Still assumes the internal API is wired end to end (item-0001).

Absorbed from the item-0011 completion report: the second axis. Declaring a
CUE field without the optional marker does not make it required in the
exported JSON Schema when its type is a list. CUE gives a list type an
implicit empty-list default, and the exporter drops a defaulted field from
the required set, so no array property anywhere in contract/lane.schema.json
is required. Seven definitions are affected -- Capture (command, mounts,
peers), CaptureSet (captures), ImageConfig (cmd, entrypoint), PackSpec
(files), SSH (knownHosts), Step (args, inputs, outputs, peers, secrets), and
TrustedRootReplica (certificateAuthorities, ctlogs, timestampAuthorities,
tlogs) -- and several of those fields are written without the optional
marker, so the contract reads as requiring what the gate does not check. The
effect is that strike validate accepts a lane omitting the field and the
omission surfaces later, at runtime, if at all: an inline trust root with no
ctlogs block validates clean and is rejected only when ParseTrustedRoot runs
at verify time. Some of these lists are genuinely optional and their
declarations should gain the optional marker instead; the item owns drawing
that line once and enforcing whichever side each field lands on. This shares
the lint step and the build-gate wiring with the layer-direction rule, which
is why it lands here rather than as its own item.

Amended 2026-08-25 at dc83c97, from a grounding pass over the item's own
references. Four corrections, none of which change what the item is for.

The tools/lintfrom mold is gone: the linter and its lint-from gate were removed
in a66025c with the DAG reduction (item-0068), recorded as an append-only
amendment on ADR-046 -- its premise died with the resolved edge structs and it
would now forbid the sanctioned consumer API. The link is repointed and the
mold reference dropped, because an authoring session can no longer read the
tool it was told to imitate.

The host fork gains its real third arm. tools/cuelint already lints CUE source
under contract/ and carries three rules of exactly this class (inline string
disjunction per ADR-049 rule 5, a re-inlined primitive grammar, a lossy map
key), so the layer-direction rule is a fourth rule on the same source, and
under code-is-liability that is the option to weigh first rather than one the
item omits. It comes with a constraint the item did not state: cuelint is
deliberately standalone and outside the aggregate lint target, run on demand
rather than gating, so hosting the rule there does not by itself satisfy the
mandatory-wiring requirement.

Sequencing is unaffected but has one downstream touch. This item is scheduled
well ahead of item-0094, which takes cuelint go-native and renames it to
lintcue, so it lands in the Makefile era and names a make target. If it adds a
gate target of its own, that target is not in the rehome list item-0096
enumerates, which makes item-0096 an amendment candidate once this lands.

item-0001 is done, so the closing assumption about the internal API being
wired end to end is satisfied and no longer an open precondition.

The .go-arch-lint.yml exclude comment still cites lintfrom as its example of
custom tooling. It is a one-line stale reference with no other owner --
item-0064 covers relative markdown links, not YAML comments -- and it is
adopted here because this is the item that retires the reference.
