Closes the measured duplication between the two Go-type linters (comparison A of
the tooling review): a shared strike-named-type resolver, a shared allowlist
idiom, and a shared package loader, duplicated across two modules. More deeply,
linttypeconv's conversion-ownership check is a subset of the conversion facts the
linttypeflow extractor already emits, so it folds in as an ownership gate over
existing facts rather than a second detector.

golangci-lint constraint (hard): linttypeconv is today the go/analysis analyzer
form (golangci-consumable via a custom plugin); linttypeflow is a raw go/packages
CLI. The merge must preserve an analyzer entrypoint, not collapse into a
make-only CLI. Dual-run is the target -- golangci-lint plugin and standalone
binary, both go-native, neither needing make or a shell. That is the same
beta-readiness direction the README first sentence implies ("no shell, no local
toolchain"): keep the tools go-native so the Makefile wrappers can fall away when
make is retired (item-0035 and the beta-readiness arc), rather than adding a
second orchestration layer.

Execution design fork (drift-invariant, resolve at execution): reconcile
linttypeflow's -report JSONL survey (all fact kinds, standalone, exit zero) with
the go/analysis diagnostic model (per-finding gates). The likely shape is
analyzer(s) for the gates plus a standalone -report entrypoint reusing the one
extractor; decide the exact split against the code at execution.

Sequencing: depends on linttypeflow (item-0073). Best sequenced after the
escalation and standalone-to-aggregate graduation (item-0084) settle the gate
surface, so the merge does not race structural change to the extractor. Naming:
gotypelint (suffix convention), paired with cuelint on the CUE side.

Measured against golangci-lint for the plugin half of this item. The
${base-path} placeholder is substituted only for the built-in linters that take
a replacer, and the module-plugin builder passes its settings block through
untouched, so a custom plugin cannot receive a resolved base path and must
locate the tree itself. A plugin module also maps to exactly one golangci-lint
linter name: BuildAnalyzers may return several analyzers, but all of them
report under the single settings key. The go/analysis report hook validates
only suggested fixes, so a diagnostic positioned in a file outside the analyzed
package is accepted and printed by the standalone driver; whether
golangci-lint's own issue processors keep such a diagnostic is the open
question this item must settle before the fold.

Amended 2026-08-26 at ae4fa89: tools/lintdocs is folded in. Its ASCII and
ADR-index analyzers landed with item-0095 behind a multichecker and the
lint-docs make target, whose own comment states the target is retired once
golangci-lint adoption lands. No item owned that adoption, and item-0096 does
not list lint-docs among the wrappers it rehomes, so the gate would have lost
its entrypoint when the root Makefile goes. Folding it here rather than into a
new item follows the precedent item-0094 sets for cuelint: the item that makes
a tool go-native also deletes its target.

Fold means adoption under one plugin entrypoint, not merger into gotypelint.
The lintdocs analyzers read Markdown and the ADR index and carry no
strike-named-type resolver, no allowlist and no conversion facts, so there is
nothing to deduplicate against the Go-type gates. Only the golangci plugin
idiom is shared, which is why doing it once here is cheaper than inventing it
twice.

lintdocs is also the sharpest instance of the open question this item already
carries. Its analyzers position diagnostics on Markdown files that belong to
no analyzed package, so whether golangci-lint's issue processors keep such a
diagnostic is not a side question for it but the whole gate, and its checks
locate the module root themselves rather than taking a base path, which is the
exact constraint measured for the plugin half. Settling the question against
lintdocs settles it for the Go-type gates too.
