Two outbound-HTTPS constructions coexist in production and are not equivalent.
The registry push path dials through transport.DialVerified, checks the dial
address against the declared authority, captures the observed server identity,
and rejects plaintext structurally through a failing DialContext. The keyless
Fulcio, Rekor and TSA clients install a bare TLSClientConfig: no address
binding, no identity capture, no plaintext rejection. Both serve declared peers
carrying declared trust, so the difference is not derived from the peer model.

Whether that difference is a defect or a deliberate role distinction is the
open question this item settles. The push peer is recorded in the attestation;
the sigstore endpoints may or may not warrant the same treatment. Either answer
is acceptable, but it has to be chosen and written down rather than left as the
residue of two authors.

The consolidation is deliberately not behaviour-neutral: absorbing the keyless
path into the verified-dial form adds identity capture where there is none
today. That is why it cannot ride inside the golden-generator work, which
merely needs the client builder to be reachable from a module-local tool.

Three smaller duplications fall out with it and should not be chased
separately: the https-only round tripper exists once in the deploy push path
and again under a different name in the cmd integration test; the round-trip
timeout is declared twice with the same value under two names; and the client
builder itself is written twice, once in the keyless chain and once in the test
harness scaffolding. Whether the resulting owner lives in transport is part of
the decision, not a premise -- transport's charter today is carriage, and an
http.Client factory may or may not belong to it.

## Amendment 2026-08-30: the stronger construction is the mediator's, not the push path's

The item was written on the premise that the registry push path is the stronger
of the two outbound constructions and the keyless clients should be absorbed
into it. Grounding against the tree while planning item-0049 showed the premise
is wrong in a way that matters.

transport.DialVerified hands the declared authority to a bare net.Dialer, so a
declared name is resolved by the system resolver. That is a DNS-based routing
decision taken outside the lane's declared resolver -- precisely what
transport.DialTCP's own doc comment rules out for the step path ("A name cannot
be passed ... The parameter type is what enforces that"). Absorbing Fulcio,
Rekor and TSA into that construction would spread the defect rather than
retire it.

The construction that is actually correct is internal/mediator's dialUpstream:
it resolves through the declared DoT resolver, dials the resolved address via
DialTCP, sets the verification name separately, and captures the observed
identity. Routing and identity are two values there, not one. Its five steps are
a hand-rolled inline copy of what DialVerified does, written that way only
because DialVerified cannot accept an already-resolved target. This item now
moves that form down into transport and makes it the owner.

Two consequences worth naming. The SNI-from-address inference exists only to
guess identity from routing; once the two are separate parameters the guess is
impossible and the branch goes away. And a peer declared as an address literal
stops being a special case, because nothing derives a name from the dial target
any more -- that is a behaviour to pin with a test, not to assume.

Open question for authoring: Go uses one tls.Config field for both the SNI it
sends and the name it verifies. item-0080 requires the mediator to verify
against the lane declaration while forwarding the container's SNI. If those must
differ byte-for-byte the shared construction needs two name parameters and its
own certificate verification; if canonicalization makes them equal in practice,
one parameter suffices. Settle this at authoring, against item-0080's intent.

Boundary against item-0080: a lookup capability has to be declared somewhere
transport can see, and transport sits below capsule and mediator, so the three
identical upstream-lookup function types collapse here as a side effect. The
retype to the canonical-host type stays item-0080's work, not this item's.

Boundary against item-0049: the resolver restructuring depends on this item and
not the reverse. item-0049 introduces primitive.IPLiteral and the DoT endpoint,
then consumes the construction this item establishes; the DoT resolver is the
base case that cannot resolve because it is the resolution.

Whether the control plane resolving through the declared resolver warrants an
ADR is open. ADR-028 governs step-container egress and does not reach the
control plane.
