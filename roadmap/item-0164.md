Found by the first executor run of item-0162 on 2026-10-25: a container
step declaring output image fails after the step exits, at "normalize
image output: wrap image: read OCI tar: archive/tar: invalid tar
header". Read at b561c4d, no build: the producer commits the held
container and exports it with the engine image save, whose default
format is oci-archive, so the stream is the layout itself; the helper it
feeds was written for the earlier image output type, a layout file the
step wrote and the engine container archive wrapped, and it unwraps the
first regular entry, a blob. The mismatch dates from 29155bb
(2026-06-21, item-0001), which changed the producer and kept the helper.
No test reached the path: every active image output sits on a pack step,
and the one container-step image-output fixture was parked in f872d43
(2026-08-09) for an unrelated reason.

Fixing the unwrap alone would not make the output correct. ADR-035
rejects container commit explicitly: under the read-only root of the
hardened profile a commit captures an empty top layer and excludes the
workdir volume, so the image would hold the base and none of the step's
work. The commit is also not reproducible: the libpod commit endpoint
takes no timestamp, podman sets none, and buildah stamps the config and
history with the current time, while the wrap sets manifest annotations
only, so the config digest changes on every run, against ADR-046's
reproducibility principle.

Operator decision of 2026-10-25: option A, remove. Rejected: option B,
fix only the unwrap (it would silently produce the base plus an empty
layer under a moving digest), and option C, normalize the commit (it
rebuilds pack). The use case of a step that builds a base image is
covered by a directory output packed onto a digest-pinned base and run
through imageFromStep. Runs directly after item-0162, whose live fixture
does not depend on the removed path.

What the restriction means for imageFromStep, reviewed at ebc4158: the
validator already requires the producer to declare an image output, so
with the new rule the producer is a pack step and imageFromStep needs no
rule of its own; resolution, spec hash and cache are unchanged. Every
executable lane-generated image is then control-plane assembled, which
makes ADR-045's premise -- the control plane computes the digest over
bytes it observed -- hold without exception, keeps consumer cache keys
stable, and lets the base-SBOM collection over pack bases cover every
imageFromStep chain. Two consequences, both in scope by operator
decision of 2026-10-25. First, the boundary of one pack: a pack base is
an externally declared digest, so a lane cannot build an image on a
lane-built image; it is recorded in the ADR-046 amendment, and a base
taken from a step would be a later extension. Second, the pack base
fetch becomes the only path that produces an executable lane-generated
base, and today it resolves an index to go-containerregistry's default
platform, linux/amd64, whatever the engine runs; on another platform
every imageFromStep chain would start from the wrong base. The engine
identity and the selection rule item-0162 added for step images are the
pieces the fix reuses.
