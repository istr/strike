Discovered while landing item-0153. The README lane snippet had carried four
schema errors for months -- name: instead of id: on the step and on both
outputs, and no resolver, oidc or keyless block -- and nobody noticed, because
nothing in the tree reads those blocks. The ADR-056 documentation pass corrected
them by hand, which fixes the instance and not the class.

Two things make this more than a parse loop. Documentation examples carry a
named placeholder for the trust anchor by ratified decision, not a certificate:
a real anchor is 596 characters of noise in a fifteen-line snippet, and the
fixture anchor in particular stands over a private key RFC 9500 publishes, so a
copyable example would declare an anchor anyone can mint against. The gate
therefore substitutes before it parses. And a fenced yaml block in a markdown
file is not necessarily a lane fragment -- some are compose files, some are
frontmatter, some are deliberate counter-examples -- so the in-scope criterion
has to be stated rather than guessed.

Open question for whoever takes it: whether the gate lives in tools/lintdoc,
which already walks the whole tree and owns the placeholder convention through
the trust-anchor allowlist, or in a tool of its own. lintdoc has the walk and
the file-kind boundary already; against that, it currently needs no CUE and this
would give it one.

Amended 2026-11-07 at e63a58c: the walk question widens. lintdoc's tree
walk skips only .git, so it also scans the git-ignored files in the module
root, where operator instruction, supplement and report files live by
convention. Those files carry byte-exact snippets: an instruction that
dictates a new base64 DER blob and admits it to the allowlist only in a
later commit turns make lint red for every earlier commit, with the finding
pointing at the instruction file itself (item-0186 part 2 ran its first
gates with the instruction file moved aside). The same files carry fenced
lane fragments, so a snippet gate on the whole-tree walk would read them
too. The current behavior is also a constraint others plan around:
item-0185 kept the live trusted root off disk because the walk includes
ignored files, and item-0007 does the same. Tracked root documents match
the same /*.md ignore rule, so the distinction is not visible from the
filesystem, and git cannot be asked (no subprocess). Whoever takes this
item states which ignored root files the tree-wide checks cover, by a
criterion written into lintdoc rather than inferred.
