Item-0122 removed every production import of go-containerregistry's layout package and gated the property with forbidigo, leaving three ratified test-scaffolding exclusions. Investigation against the pinned v0.21.9 source established that the package's core type is a bare filesystem path with no fs.FS, io.Reader, or io.Writer seam anywhere, and that OCI image-layout serialization is the one thing go-containerregistry has no in-memory form for -- its tarball package handles docker-save format only and rejects layout tars. Two of the three sites reach that API only to parse index.json and can be rewritten against the standard library; a third can hand production's exact bytes to the engine, which is a stronger independence claim than re-serializing them through the same library strike already depends on. The site worth keeping is the independent writer that production readers are tested against: rewriting it in the standard library would reproduce production's own algorithm and create a convergence risk where one shared wrong assumption passes forever. The open decision is where that single conformance point lives -- the existing writer, or a standard-library writer plus one canary test that round-trips production output through the third-party reader. A latent defect found during the investigation belongs here rather than alone: the wrap test's index reader returns an empty digest and a nil error when the index carries no manifests.
