Proposed by the roadmap revision behind ADR-055 from the M2 side finding,
with one correction the operator confirms or refutes before ratification.

M2 records that the readiness probe "has no timeout of its own and fails
as a silent hang". At c01be87 internal/testutil/harnessrecover.go bounds
the readiness phase with readyBudget (180 s), each request with
probeTimeout (10 s) and the retry pause with pollInterval (2 s), all as
context deadlines, and the file has not changed since item-0130 landed
(a7682a6), before the spike's anchor. A silent unbounded hang is
therefore not what the code does. The likely observation: without host
networking the failure is connection refused, deterministic, yet the
probe retries it for the whole budget as if the service were merely not
ready; with several RequireHarness callers in one package the 180 s
budgets add up past the go test default of ten minutes, which reports as
a timeout with the probe loop in the goroutine dump. If that is what the
spike saw, the defect is the one this item names: no distinction between
unreachable and not-ready, and a budget per call rather than per
package. If the spike saw something else, this item is restated to it.
