Created by operator decision of 2026-11-06 (fork H1 of the item-0173
preparation). Operator rule of 2026-11-05: inside a lane run nothing
resolves through system DNS and every host the run reaches is declared;
strike verify declares nothing about registry identity.

Found at 44689a1: three controller-side reads inside strike run use
go-containerregistry's default transport, so they resolve through the
system resolver and trust the system roots -- the pack base fetch
(internal/executor/pack.go through registry.FetchImage), the base-SBOM
referrer fetch and the keyless trust-root fetch of the deploy
(internal/deploy/base_sbom.go). Only the deploy target carries a host and
an anchor today; the pack base and trustRootRef are bare image
references. The run's transport.Dialer offers DialPeer with a pinned
anchor and LookupHost, nothing else.

History: the lane-wide registry string (no anchor) was the engine-push tag
prefix and was removed with ADR-051 (1da3a0b); the OCI peer type was
removed with ADR-029 (d13ba71), which named a controller-pull registry
allowlist as "a distinct lane-level field, not a peer" if wanted later.
Peers stay container egress; this item adds that lane-level field.

Decided (2026-11-06): the declaration is lane-level in the endpoint TLS
shape (H2 a); the engine's own pull of step images stays out of scope,
because strike does not control the engine's resolver, and is recorded as
a known boundary (H5). Open until authoring: the anchor form for public
registries -- a pinned rootca under the existing #CertificateMode, or a
new mode (H3).

Measure before authoring (H4): the redirect targets, and their stability,
of anonymous blob GETs for the base images the tree uses (cgr.dev today).
In a run the transport dials declared hosts only, so a registry that
redirects blobs to a storage or CDN host fails the pack base fetch unless
that host is declared or not needed.

This item takes the in-run half of fork G6' from item-0173; item-0173
keeps the verify side and depends on this item.

## Amendment 2026-11-06 at 47b4bc1: five reads, storages, the strict reference rule

Operator decisions of 2026-11-06, taken after the H4 spike at 584b66a;
the goal, the acceptance intent and the links above are restated to
match.

Scope. The engine never pulls: since ADR-045's amendment of 2026-10-25
the controller fetches every external step and capture image itself.
H5's premise therefore does not hold, and those two fetches join the
pack base, base-SBOM referrer and trust-root reads -- five reads, all
anonymous in a run, all through the declaration and the run's transport.

Measured (H4). Every anonymous blob read at cgr.dev is answered 307 with
a presigned URL on one Cloudflare R2 account host, which Chainguard
documents by exact name; ping, token realm, manifests and referrers stay
on cgr.dev. A survey of the major registries found the same pattern
nearly everywhere: only Google Artifact Registry is observed to serve a
pull from a single host, and that is undocumented.

Shape. A registry entry is a registry endpoint plus an optional list of
storage endpoints, both in the endpoint TLS shape, under the field names
registries, registry and storages. A storage is reached only as the
redirect target of a blob read of its own registry; a redirect to any
host not declared under that registry fails hard, which prevents one
registry's redirect from reaching another's storage. Same-host
redirects are followed. Every host is declared once across registries,
storages and deploy targets; a deploy target has no storages. The
anchor mode is not narrowed. Public registries are pinned by the root
their chain verifies to (H3): GTS Root R1 for cgr.dev and GTS Root R4
for its storage host.

References. The written registry of a reference must equal the registry
go-containerregistry dials, so docker.io and host-less references are
rejected and the implicit rewrite is gone; the default port is never
spelled out; an uppercase registry host is rejected with its own
message. Reads in a run are https only.

Tests. Fixtures name a fictional images.example.com for their images;
the live integration lanes resolve through the public DoT resolver, as
the bootstrap lane does, because the harness resolver serves no public
names.
