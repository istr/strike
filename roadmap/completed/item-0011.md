## Final summary

Landed as commit 3dd5a9d. strike verify now reconstructs the precertificate the CT log signed -- the leaf TBSCertificate with the SCT list extension removed, prefixed by the sha256 of the issuer SubjectPublicKeyInfo -- and checks the log ECDSA signature over it offline, per RFC 6962 3.2, in a new internal/verify/sct.go behind the ErrSCT sentinel. Exactly one SCT is required rather than a threshold of one. ADR-053 is implemented for both transparency logs: the CT key is bound to the SCT own timestamp inside the signed structure, the Rekor key to the RFC3161 trusted time, because Rekor v2 signs no time of its own. Leaf returns the issuing certificate alongside the leaf so both layers rest on one chain build. The trusted-root CUE replica hoists a shared #TransparencyLogReplica projected by both tlogs and ctlogs, carrying both validity bounds. All three golden bundles still verify with enforcement active, and a new TestGoldenCTMutations rejects each of an unknown log id, a key that did not sign the SCT, and a window excluding it. Three notes for whoever works this code next. First, ctlogs is enforced in Go by ParseTrustedRoot, not by lane validation: a lane declaring an inline trustRoot with no ctlogs block still passes strike validate and fails closed later at verify time. That is an instance of the general CUE list required-ness gap, absorbed into item-0016. Second, Inclusion sat at exactly the gocyclo ceiling of 15 before this change, so the two new guards live behind checkpointUnderTrustedKey rather than inline; the function is at the ceiling again and the next layer added to it will trip the gate. Third, the ephemeral instruction for this run omitted its own CUE schema step while requiring the file in its acceptance gates, and its withinWindow grep criterion counted three lines where the definition doc comment makes four; both were reported rather than worked around.
