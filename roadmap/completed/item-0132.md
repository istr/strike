Established mechanism, verified against the running host: rootless podman keeps
conmon, pidfiles and the network namespace under XDG_RUNTIME_DIR, and elogind
removes /run/user/$UID when the user's last session closes. The containers are
never signalled -- they lose the directory their monitors live in -- which is
why podman records no died/stop/kill event and why FinishedAt is the zero value
on every container. Everything durable survives: container definitions, the
three named volumes and the network JSON all live under the GraphRoot on a
persistent filesystem, so recovery is a restart of a clearly bounded volatile
layer, not a re-creation.

Ratified scope, 2026-08-20. The repository owns recovery and the rotating
anchors; the operator owns creation. A cold start stays podman compose up and
is required only when container definitions are absent or no longer match the
declared images -- after down, clean, a manual remove, a fresh clone, a
GraphRoot loss, or a structural edit to compose.yaml. A plain restart does pick
up changed bind-mount contents (Caddyfile, fulcio and zot config, the whole pki
directory) but not the image digest, command, ports, aliases, environment or
mount list, which are baked in at create time. That is why the warm path needs
a drift guard: without it, raising a digest and restarting would silently run
the old image, which contradicts digest-pinned external references.

Lands in two commits: first the engine surface (a label-filtered container list
and an idempotent start by id), then the recovery path in test scaffolding plus
its two call sites and the documentation. Two commits, two review concerns.

Ratified shape decisions: the recovery path drives the engine through
internal/container rather than a second test-local HTTP client, because that
package is the chokepoint enforcing the TLS floor on TCP engine connections and
carrying the audit transport; the poll interval is expressed with a
context-scoped deadline rather than a new time primitive; readiness gates keep
parity with what the Makefile probed, with full coverage deferred to item-0134;
the golden trust root is untouched, item-0007 owns the live one; and the entry
point is a helper called from the two live tests, not a TestMain, because those
two tests are one of 62 and one of 48 in their packages and a TestMain would
drag the hermetic majority onto the engine.

Open question the first execution answers on its own: whether the two Caddy
network aliases resolve in-network after a warm start, since aardvark-dns also
keeps state under XDG_RUNTIME_DIR. A green live keyless test settles it.

Sequencing note: item-0131 regenerates the keyless goldens through the golden
generator, which assembles the trusted root from the exported TSA chain but
only checks that the file exists, not that it is fresh. Running it against a
chain from an earlier harness incarnation produces a golden set that is
internally inconsistent for the first time. This item provides the refresh that
must precede that run.
