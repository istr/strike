Finding at 7b09365: three documents describe three topologies for stage_3
(ADR-009 says inside stage_2, README says inside strike:stage_1, SECURITY.md
says a nested engine inside the stage_2 step). The stage_2 image the lane
packs is chainguard static plus the binary and carries no engine; a strike in
it can only build if a step container reaches the stage_1 engine or starts one
of its own, and both are excluded by the non-configurable ADR-005 profile
(cap-drop ALL, read-only rootfs, network none unless declared) and by ADR-055
D5. A second finding shapes the compare: an image output is addressed by step
and cannot be mounted as a file input (ADR-046), so the compare needs a step
kind of its own (item-0158).

The single nesting of stage_1 itself was weighed on 2026-09-14 and retired.
What nesting offers is real but is not trust: least privilege for the
control plane (the inner socket instead of the host socket), ephemeral
engine state on tmpfs, an engine configuration pinned by the image, and
independence from the host engine version. What it costs decides: the
trusted computing base grows by an unattested engine image while the host
engine stays inside it (it starts and can inspect the container), the
isolation boundary between a step and the control plane is identical in
both topologies, the operator container needs relaxed confinement (proc
unmask, nested user namespaces) that nothing else in the tree needs and
that ADR-055 D7 never measured, the proof runs in a topology used nowhere
else, tmpfs storage must hold every image and the build, and two modes
force two builder ids. Verified the same day: no trust-bearing engine image
exists to shrink that cost -- the public chainguard-images build-config
repository lists 54 free images and none of podman, buildah, buildkit or
skopeo; wolfi-dev/os on main carries no podman and no passt package, so a
self-built engine image would have to build both from source.

The principle that results extends ADR-001 (engine via API) and ADR-055 D1/D2
(the engine is the one host capability; everything else is an image) to a
closed figure. Its scope is strike's execution path: a harness service that
happens to be a container runtime (the k3s deploy target of item-0141) is a
target, not an executor, and stays permitted; a future remote engine over
mTLS is a client-of-one-engine case and stays consistent. Optional structural
enforcement, not required here: a lintdoc rule that no Containerfile in the
tree installs an engine.

Background: the review report of 2026-09-14 (strike-adr009-bootstrap-review)
and the two companion reports on compiler versus build-tool bootstrapping and
on a SLSA L3 Go control plane.
