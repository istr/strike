Found by the item-0156 spike of 2026-10-24 (ADR-055, amendment of that date,
point B4). Every strike controller on an endpoint runs with host networking,
so all of them share one loopback; capsule ports were allocated
deterministically in lane order from one base, so every controller asks for
the same ports. Measured with two bootstrap controllers: the second failed at
its first unit on the resolver TCP bind, after its resolver UDP bind had
succeeded over the first controller's thanks to SO_REUSEADDR, and a probe of
the same bind sequence showed the newer UDP socket receiving the datagrams.
Derived, not measured: a second controller can fail mid-run, and a bootstrap
beside an integration-test run from the dev container collides the same way.

Operator decision of 2026-10-24: option B, kernel-assigned ports at unit
start, recorded in the ADR-033 amendment of that date. Rejected: keeping the
allocator and documenting one strike run per endpoint (option A), and a
random per-run base (option C), which lowers the collision rate without
removing it and keeps the UDP window.

Determinism of the ports buys nothing that is checked: they enter neither the
step spec hash nor any attestation, and ADR-037 already names host ports as
selectors that are never trust anchors. The front already binds a
kernel-assigned loopback port. pasta takes separate host ports for its TCP
and UDP forwards, so the three listeners need not share a number.

Interaction with item-0080: that item retypes the unit key the port
allocation and the records are keyed on. This item deletes the allocation
side of it; whichever lands second drops or narrows the overlapping clause.
Point to confirm at authoring: every caller starts the capsule before it
reads the pasta arguments.
