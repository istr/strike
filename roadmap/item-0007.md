The original cosign smoke was overtaken by strike's own live test (TestKeylessLive); this independent verifier path remains. Belongs to the instruction-5 arc.

Amended 2026-08-19 after running the check by hand against a live harness.
Rationale, short version: the property this item asserts is true and has now been
measured, so the scope narrows to the two things that are actually missing --
the assembled trust root and the gate.

Measured. cosign v3.1.1 verify-attestation, against the subject the
registry-deploy itest pushes into the harness zot and referenced by digest,
exits 0 for all three predicate layers: sealed SLSA provenance, engine-context,
informational. cosign reports the claims validated (subject binding on, not the
--check-claims=false the conformance target uses), transparency-log existence
verified offline, and the code-signing certificate verified against the trusted
CA. Only the registry is contacted. Referrer discovery works even though strike
sets artifactType through the config fallback rather than the manifest field and
annotates dev.strike.statement rather than cosign's
dev.sigstore.bundle.predicateType: cosign selects on --type from the signed
statement, so neither divergence blocks it.

Missing, first: the assembled trust root. The only trusted_root.json in the tree
is the golden test fixture, and verifying live bundles against it fails with
"pkcs7: No certificate for signer" because the harness TSA mints a fresh signing
cert per startup. The hand run above passed only after splicing the freshly
fetched pki/tsa-certchain.pem into a copy of that file. That assembly, plus its
refresh after a restart, is this item's deliverable. Note that make
tsa-certchain does not cover it -- it refreshes the exported chain but not the
golden root -- and make conformance keeps passing regardless, because the golden
bundles and the golden root were timestamped together and stay self-consistent.

Missing, second: the gate. Nothing in the repository runs verify-attestation;
the only committed cosign check is the harness conformance target, which
verifies golden files with verify-blob-attestation and claims checking off. This
pairs with item-0010, which owns that weaker file-based property, and with the
registry-deploy itest, which already produces the subject and its five
referrers.
