The produce path computes each output layer's diff_id control-plane-side, before the assembled image is ever loaded into the engine, so a consumer that recomputes sha256 over the uncompressed layer and compares it against the handle terminates at a value strike itself produced. The cache-hit path does not: registerCachedOutputs exports the cached image and takes the handle's diff_id from the config the engine returned. A later consumer check against that handle therefore binds two exports of the same image to each other, not to bytes the control plane produced, and an engine that answers consistently defeats it. The same gap exists for image outputs and is closed there by refusing to cache a step whose image a deploy seals (sealsArtifact); file outputs have no equivalent, and a cached file output can be delivered into a pack step whose own image is sealed. Whether that indirection is acceptable is a trust-boundary question about what a verifier may conclude from the attestation, not a code defect, which is why the resolution may be an ADR rather than a change.

## Amendment 2026-10-25 at 013959b: the pack cache key

Found by the item-0158 analysis, read at 013959b, no build. The run path
feeds a step's spec hash with its container inputs only, and the spec hash
covers the image digest, args, env, and the input and source hashes. For a
pack step the image digest is the base digest and there are no container
inputs, so its key is the base digest plus args and env, which a pack step
does not use. Neither the pack files, nor the image config and annotations,
nor the spec hashes of the producers the pack reads enter it. A pack step
that no deploy seals is therefore restored from cache after its producers
changed, and every imageFromStep chain built on it starts from the stale
image. Sealed pack steps are unaffected, being never cached, and so is the
step a registry deploy gate names in reproducedBy (item-0158). The item-0164
landing summary named a further input the key does not cover: the engine
platform the pack base resolves to; it is the same defect. The README states
that the spec hash covers the spec hashes of producing steps, which is not
true of a pack step.

Operator decision of 2026-10-25: this item owns the defect rather than a new
one, because both halves concern what a cache hit may be trusted to deliver.
