## Amendment 2026-08-31: three grounded defects, and one constraint that must survive

Found while establishing the resolved-and-verified dial owner in item-0130, by
reading internal/container rather than reasoning about it. All three are in the
https engine form only; the unix socket form goes through
transport.DialUnixSocket and is clean.

First, the address is resolved by the system resolver. newHTTPClient sets
TLSClientConfig and nothing else, so http.Transport uses its default dialer and
its default resolution. parseEngineAddress accepts any authority the https
grammar admits, so this is a real name path, not a theoretical one.

Second, no identity is captured. The https form performs a genuine TLS
handshake and no CaptureIdentity call observes it. ADR-030 exempts the engine
record on the ground that it "may describe a Unix socket with no TLS
handshake", which is true of one of the two admitted forms and not of the
other; the exemption is therefore wider than its stated reason. ADR-030 gains
an amendment when this item lands.

Third, the trust anchor is implicit by default. internal/container/tls.go
states it outright: with no CAFile configured, RootCAs stays nil and Go uses
the system CA store. That is the concrete reason hardenedByDeclaration is
false today, and it is a declared-anchor defect of the same class the peers and
the resolver do not have.

The constraint that must survive: the engine address must NOT be resolved
through the lane-declared DoT resolver. The lane is input; the engine is the
substrate that executes it. Letting a lane influence how strike reaches its own
control connection is a privilege inversion. This is worth stating because
item-0130 made every other outbound dial resolve through the declared resolver,
so a later consistency pass has an obvious and wrong reason to make this one
match. Ordering supports the same conclusion without carrying the argument:
initEngine runs before the lane is parsed, so no lane-declared resolver exists
yet -- but that is a consequence of the current call order and not a reason, and
the reason is the one above.

Scope note: the system-CA fallback is a security defect that does not depend on
the shape consolidation this item is blocked on. If it should land before
item-0004, it separates cleanly into its own item; leaving it here is a
deliberate choice to keep the engine's declared-versus-observed story in one
place.
