# Compiler Three-Stage Bootstrap vs. Build-Tool Bootstrapping: What Transfers, What Doesn't, and Who Actually Does It

## TL;DR
- The classic three-stage compiler bootstrap (canonically GCC) exists to (i) escape the chicken-and-egg of a self-hosting compiler, (ii) let a possibly-weak host compiler be replaced by an optimized self-built one, and (iii) run a fixed-point self-consistency check -- **stage2 vs stage3 must be bit-identical**; it is emphatically **not** a proof of correctness and does **not** address Ken Thompson's "trusting trust" attack (that requires Diverse Double-Compiling).
- For build tools the identity/fixed-point comparison does **not** transfer 1:1: a build tool's output is an orchestration executed by *external* compilers, so "tool built by stage1-tool vs by stage2-tool" is trivially identical unless orchestration behaviour differs -- only purpose (i), the stage-0 chicken-and-egg problem, transfers strongly, and almost every serious build tool already solves it.
- The closest real-world analogue to a genuine multi-stage self-bootstrap-with-verification among build tools is **Gradle's "Gradleception"** CI job (builds Gradle with a freshly-built Gradle, twice, using fixed timestamps for reproducibility), but **no** mainstream build tool performs a mandatory bit-identical stage2-vs-stage3 compare the way GCC does; the true fixed-point verification in this space lives in reproducible-builds tooling and in full-source bootstrap chains (GNU Guix, nixpkgs stdenv, live-bootstrap).

---

## Key Findings

1. **GCC's `make bootstrap` = stage1 (built by host cc) -> stage2 (built by stage1) -> stage3 (built by stage2), then a bit-for-bit compare of stage2 vs stage3.** The comparison is stage2-vs-stage3 (not stage1-vs-stage2) because stage1 was built by a *foreign* compiler and legitimately differs; stage2 and stage3 are both built from identical sources by *GCC-built* compilers, so they must match. A mismatch signals a serious bug (miscompilation, UB/uninitialized data, nondeterminism). `bootstrap4` adds a stage4 for debugging.
2. **"Three" is not universal.** Rust uses stage0 (downloaded beta) -> stage1 -> stage2; GHC uses stage0/1/2 with an *optional* stage3 "self-test" whose object code should equal stage2's; Go's `cmd/dist` builds toolchain1/2/3. **Go does not diff toolchain2 and toolchain3** -- toolchain3 exists for build-ID/caching reasons, not verification.
3. **The trust argument is widely misunderstood.** Self-bootstrap != trust. Only DDC (Wheeler) plus reproducible builds actually counter Thompson's attack.
4. **Build tools are heterogeneous** -- executors (make, Ninja), generators/meta-build (CMake, Meson, Autotools, GN), and integrated systems (Bazel, Buck2, Gradle, Maven, Cargo, the `go` command). Some are compiled programs (make, ninja, cmake, bazel), some interpreted (Meson, SCons, waf -- Python), some JVM (Gradle, Maven -- compiled by javac/kotlinc, *not by themselves*).
5. **Almost every compiled build tool solves the stage-0 problem** with a from-scratch script (make's `build.sh`, CMake's `bootstrap`, Ninja's `configure.py --bootstrap`, Bazel's `compile.sh`), then rebuilds itself with itself. **Only Gradle runs a multi-stage self-build in CI as a routine correctness gate.**
6. **Two different meanings of "bootstrap"** collide in build-tool land: (a) `./bootstrap`/`autogen.sh` scripts that merely regenerate `configure` (autotools/gnulib) -- NOT self-hosting; (b) the self-hosting build-tool-without-the-tool sense the user is asking about.

## Details

### PART 1 -- The three-stage compiler bootstrap (GCC as canonical example)

**The mechanism.** GCC's top-level `make bootstrap` performs, per the official *Installing GCC: Building* documentation (gcc.gnu.org/install/build.html):

- **stage1**: the GCC source is compiled by the pre-existing **host/system compiler**. This stage1 compiler may be slow or built with a weaker/older compiler; its only job is to be able to compile GCC again.
- **stage2**: the *same* GCC source is compiled by the **stage1** compiler.
- **stage3**: the *same* GCC source is compiled by the **stage2** compiler.
- **compare**: GCC then performs "a comparison test of the stage2 and stage3 compilers," and builds the runtime libraries with stage3. The GCC internals manual states the compare step "ensures that the compiler is running properly, since it should produce the same object files regardless of how it itself was compiled."

**Why stage2 vs stage3, not stage1 vs stage2.** stage1 is built by a *different* (foreign) compiler, so its generated code can legitimately differ from stage2's -- different optimizer, different code generation, etc. But stage2 and stage3 are compiled from *byte-identical GCC sources* by two compilers that are themselves *functionally equivalent GCC builds*. If GCC is deterministic and correct, feeding identical source to two equivalent compilers must yield identical object code. Therefore stage2 and stage3 must be **bit-identical**. Per the docs: "If the comparison of stage2 and stage3 fails, this normally indicates that the stage2 compiler has compiled GCC incorrectly, and is therefore a potentially serious bug which you should investigate and report."

**What a mismatch indicates:** miscompilation by the host compiler that survived into stage1's behaviour; undefined behaviour / reads of uninitialized memory inside GCC itself; or nondeterministic compiler output (e.g., hashing on pointer values, unsorted container iteration, embedded timestamps/paths). GCC even offers `make bootstrap4` "to increase the number of stages of bootstrap" when host miscompilation is suspected, comparing stage3 vs stage4.

**What it does NOT guarantee.** The bootstrap is a *self-consistency* (fixed-point) check, not a correctness proof: a compiler that is deterministically and consistently wrong will happily pass. Crucially, it does **not** address the "trusting trust" attack. Ken Thompson's 1984 Turing Award lecture *Reflections on Trusting Trust* (Communications of the ACM, Vol. 27, No. 8, pp. 761-763) showed a compiler binary can carry a self-reproducing backdoor invisible in source; recompiling from clean source with the poisoned compiler reproduces the backdoor, so a three-stage bootstrap propagates it perfectly through all three stages. The technique that actually counters this is **David A. Wheeler's Diverse Double-Compiling (DDC)** (ACSAC 2005; George Mason University PhD dissertation, 2009): recompile the source with a *second, independent* trusted compiler, then use that result to rebuild, and check the output matches the suspect compiler's self-rebuild. DDC (and all binary-from-source verification) depends on **reproducible builds** as a prerequisite.

**Separating the four distinct purposes** (this is the key analytical scaffold reused in Part 2):
- **(i) Chicken-and-egg / self-hosting independence:** a compiler written in the language it compiles needs *some* existing compiler to get started.
- **(ii) Quality/performance of the final binary:** stage1 may be built by a poor host compiler; the final compiler is built by a full-featured GCC, so it is faster/better. LLVM/Clang generalizes this: its CMake build supports multi-stage builds via `CLANG_ENABLE_BOOTSTRAP` (`ninja stage2`), `BOOTSTRAP_`-prefixed options passed only to stage2, and PGO/LTO/BOLT cache scripts (`clang/cmake/caches/PGO.cmake`, `BOLT-PGO.cmake`) that build an instrumented stage2 to optimize the final compiler. LLVM's docs explicitly note the historical link: "Historically one of the tests to verify that a compiler was deterministic would be a three stage build."
- **(iii) Fixed-point self-consistency check:** stage2 == stage3.
- **(iv) Reproducibility:** a *precondition* for (iii); without deterministic output the compare is meaningless (GCC docs note that on a few systems "meaningful comparison of object files is impossible; they always appear 'different'").

**"Three" is not universal:**
- **Rust** (rustc-dev-guide, *what-bootstrapping-does*): **stage0** is a downloaded pre-built beta rustc + std; it compiles the in-tree `bootstrap` build system, std, and rustc to produce the **stage1** compiler; rebuilding with stage1 + in-tree std yields **stage2** (the one shipped via rustup). The guide notes stage1 was built with the stage0 std so its ABI may differ; "To sanity check our new compiler we can build the libraries with the stage2 compiler. The result ought to be identical to before, unless something has broken." Rust's stage numbering is famously "off-by-one" vs GCC (`x build --stage N` means "build *with* stage N").
- **GHC** (Hadrian README + Mokhov et al., *Non-recursive Make Considered Harmful*, Haskell Symposium 2016): stage0 = installed bootstrap GHC -> stage1 -> stage2 (the primary product, needed for Template Haskell/plugins). Verbatim: "We sometimes also build Stage3 GHC as a self-test: the object code of Stage2 and Stage3 compilers should be the same." The Hadrian README adds that Stage3 is built "as a further smoke-test." The same fixed-point idea as GCC, but *optional*.
- **Go** (`src/cmd/dist/build.go`, `cmdbootstrap()`): from an older bootstrap Go it builds `cmd/dist`, then **toolchain1** (new compiler/asm/linker built by the old Go), then **go_bootstrap**, then **toolchain2** (= new toolchain built by toolchain1 + go_bootstrap), then **toolchain3** (= built by toolchain2). Per the Go blog *Perfectly Reproducible, Verified Go Toolchains*, "toolchain2 and toolchain3 should be identical." **But -- verified from current source (Sept 2026) -- `cmd/dist` does NOT diff them.** The comments in `build.go` explain toolchain3 exists because toolchain2's binaries carry build IDs (produced by the new compiler) that make everything "look out-of-date," so "we force-install everything here"; "Now that toolchain3 has been built from scratch, its compiler and linker should have accurate build IDs suitable for caching." The build runs `checkNotStale(...)` staleness checks, not a `bytes.Equal` comparison. The stage2==stage3 *property* is instead verified by the separate reproducible-build work (Go >= 1.21 toolchains are perfectly reproducible). As of the current main branch (Go 1.26 dev cycle), the minimum bootstrap is pinned to **go1.24.6**; the general rule (go.dev/doc/install/source) is verbatim: "Going forward, Go version 1.N will require a Go 1.M compiler, where M is N-2 rounded down to an even number. Example: Go 1.24 and 1.25 require Go 1.22."

### PART 2 -- Does a three-stage bootstrap make sense for build tools?

**First, question the premise.** "Build tool" is not one thing. The compiler-bootstrap logic depends on a compiler being a pure-ish function `source -> object code`, so self-application has a meaningful *fixed point at the object-code level*. A build tool is different: its primary output is an **orchestration** -- a dependency graph and a sequence of external commands -- and the actual artifacts are produced by *external* compilers/linkers that the build tool merely invokes. This breaks the analogy in a precise way.

**Semantic core of the argument.** Let `T` be a build tool and `build(X)` mean "artifact produced by using tool `X` to build source `T`". In the compiler case, the interesting object is `compiler(compiler_source)` and the fixed point is genuinely informative about the compiler's own code generation. In the build-tool case, `T_stage1 = build(T_stage0)` and `T_stage2 = build(T_stage1)` will be **trivially identical** *unless the tool's orchestration behaviour differs between versions* -- because the bytes of `T` are produced by the underlying compiler (gcc/clang/javac/rustc), not by the build tool itself. So the classic bit-identical compare mostly tests the *compiler*, which the build tool doesn't own. The compare only becomes informative if the build tool's orchestration changed: different flags, different command ordering, different generated files, nondeterministic scheduling, or incremental-build bugs.

**Mapping the four purposes onto build tools:**

- **(i) Chicken-and-egg -- transfers strongly.** make needs a Makefile executed by make; CMake needs CMake to configure CMake; Ninja needs a `build.ninja` executed by ninja; Bazel needs Bazel; Gradle needs Gradle (the wrapper). This *is* the stage-0 problem, and it is what nearly every tool actually solves -- with a from-scratch script (see Part 4). This is the legitimate, universal transfer.
- **(ii) Performance/quality of the final binary -- essentially does NOT transfer.** The speed of the produced *artifacts* is the compiler's job. The one caveat is build tools that contain their **own** compilation/analysis logic: Gradle's incremental Java compiler integration, Kotlin-DSL script compilation and annotation processing; Bazel's persistent workers; Buck2's Starlark evaluation. For those components a self-build does exercise the tool's own performance-critical code paths -- but that is a small slice, and PGO of that slice is not standard practice.
- **(iii) Fixed-point check -- meaningful only at the right abstraction level.** A bit-identical *binary* compare of the tool is compiler-dominated theatre. The *build-tool* fixed point should be checked on the **output that the tool actually produces**: for a generator like CMake, `cmake_stage1(src) -> generated build files` vs `cmake_stage2(src) -> generated build files`; for an executor, the command log / `ninja -t commands` output / Bazel `aquery` action graph; for integrated tools, the final artifacts under reproducible-build conditions. This is where a build-tool "bootstrap check" could add value -- and it is exactly what Gradle's reproducible-timestamp dogfooding and the reproducible-builds project target.
- **(iv) What the classic bootstrap CANNOT catch but matters most for build tools:** **incremental/rebuild correctness** -- missed rebuilds, stale outputs, races under parallelism. A compiler bootstrap is a clean full build; it says nothing about whether the tool correctly rebuilds *only* what changed. Tools address this with entirely different mechanisms: tup's design and its file-system monitoring, Bazel/Buck2 **hermeticity** and content-addressed action caching, Shake/Hadrian's dependency-tracking tests. A second, related point that genuinely *does* transfer: a self-hosting tool's own build description is written in the tool's own DSL, so **building the tool with the new tool tests DSL/build-logic compatibility** -- this is the actual rationale behind Gradle's Gradleception (Part 4), not a bit-identity check.

**Disambiguating two meanings of "bootstrap."** In build-tool land, `./bootstrap` or `autogen.sh` (autotools/gnulib) usually means "regenerate the `configure` script and imported gnulib files from a git checkout" -- this is **not** a self-hosting bootstrap at all. The user's question implicitly conflates this with the compiler sense (build-the-tool-without-the-tool). Both exist; only the second is analogous to the compiler bootstrap.

**The trust dimension is different for build tools, and arguably more important.** Build tools sit *upstream* of the compiler in the supply chain -- they choose the flags, environment, and command sequence. The relevant countermeasures are therefore **reproducible builds** (reproducible-builds.org; Debian's practice of rebuilding in deliberately varied environments), **DDC**, and **full-source bootstrap chains**:
- **GNU Guix full-source bootstrap** (2023): removes even the Mes/MesCC-Tools binaries, rooting the entire distribution in a **357-byte `hex0` seed** for x86; from there the documented chain is "gcc-mesboot (4.9.4) ... gnu-make-mesboot0 (3.80) ... tcc-boot (0.9.27) ... mes-boot (0.24.2) ... stage0-posix (hex0..M2-Planet) ... bootstrap-seeds (357-bytes for x86)" -- a package graph the Guix blog describes as "more than 22,000 nodes rooted in a 357-byte program." This bootstraps *make itself* (`gnu-make-mesboot0 (3.80)`) and the rest of the toolchain from an auditable seed. Guix's framing that "the 'trusting trust' attack is only a symptom of an incomplete or missing bootstrap story" is the ideological backdrop.
- **nixpkgs staged stdenv** (`pkgs/stdenv/linux/default.nix`): rebuilds the whole build environment -- including **make** -- in multiple named stages (bootstrap-stage0 through stage4, then "final"): stage0 provides prebuilt bootstrap-tools; later stages rebuild binutils, glibc, gmp/mpfr, and gcc, relinking against freshly built components, until `final` rebuilds everything else. This is a *staged rebuild of the environment*, not a fixed-point identity check.
- **live-bootstrap / stage0-posix / GNU Mes** -- the broader bootstrappable-builds ecosystem.

These differ fundamentally from GCC's three-stage compare: they are about **eliminating unauditable binary seeds** (a supply-chain/trust goal), not about a stage2==stage3 self-consistency assertion.

### PART 3 -- The theoretically sensible adaptation (reasoned proposal, not sourced fact)

Given the analysis above, a principled "build-tool bootstrap" would look like this:

1. **Mandatory stage0 -- bootstrap-from-nothing.** A script that builds a minimal working tool using only a compiler/shell and no pre-existing copy of the tool. This is the only universally justified stage and the one tools already ship (make's `build.sh`, CMake's `bootstrap`, Ninja's `--bootstrap`, Bazel's `compile.sh`).
2. **stage1 -- the real tool, built by stage0.** The production build of the tool, produced by the minimal stage0 tool.
3. **Optional stage2 -- with two clearly distinct purposes** (this is where the value is, and where it diverges from the compiler model):
   - **(a) DSL / build-logic self-compatibility:** build the tool *using stage1* (i.e., the tool builds itself with its own current build description). This validates that the new tool can still interpret its own build logic -- the genuinely useful analogue, because the tool's build script is written in the tool's own DSL.
   - **(b) Reproducibility / build-plan fixed point:** compare the *build plan* (generated build files / command graph / action graph), and -- for hermetic/integrated tools, or as a reproducible-builds check -- the *final artifacts*, produced by stage1 vs stage2. This is the meaningful fixed point, not a binary diff of the tool executable.
4. **Separate incremental-correctness tests** -- because no full-build bootstrap can catch stale-output/missed-rebuild bugs.

**Cost/benefit, honestly.** Most projects stop at two stages (stage0 + self-rebuild) because the marginal stage2 mostly re-tests the *external compiler*, which the tool doesn't own, so the cost (CI time, complexity) rarely justifies a mandatory bit-identical compare. The compiler-style bit-identical compare is **pure theatre** for a tool whose bytes come from gcc/javac and whose output is nondeterministically scheduled; it is **meaningful** only where the tool controls determinism end-to-end -- hermetic systems (Bazel, Buck2), Nix/Guix derivations, and generators whose textual output can be diffed.

### PART 4 -- Survey: which build tools implement something similar?

- **GNU make.** Ships `build.sh` -- "Shell script to build GNU Make in the absence of any 'make' program" (copyright header 1993-2024, current in `mirror/make`). Per the bootstrapping wiki quoting make's INSTALL: run `configure`, then `sh build.sh`, yielding a make you then use for `./make install`. This is a **stage0** solution (chicken-and-egg only); there is no mandated second-stage compare. Note the maintainers' explicit rationale (LWN, *Bootstrappable builds: how and why*): "We recognize that we're a fundamental build tool and that there should be another on-ramp here." Distinct from make's gnulib `bootstrap` script (regenerates configure for git checkouts).
- **CMake.** Top-level `bootstrap` POSIX shell script (in `Kitware/CMake`, current on master): builds a minimal "bootstrap cmake" with `cc`/make into `Bootstrap.cmk/`, then uses it to configure and build the real CMake. README: "Run the bootstrap script ... Once this has finished successfully, run make and make install." Once you already have a CMake, CMake builds like any CMake project (`cmake` on the source tree). **Stage0 only; no fixed-point compare.** There is community discussion (CMake Discourse, "Bootstrap-ability of CMake") noting the POSIX-only limitation on Windows.
- **Ninja.** `./configure.py --bootstrap` -- per the README, "This will generate the ninja binary and a build.ninja file you can now use to build Ninja with itself." The Ninja wiki: "Ninja is built using itself. To bootstrap the first binary ... This first compiles all non-test source files together, then re-builds Ninja using itself." So it is genuinely a **two-step self-build** (compile-all -> rebuild-with-self), but there is no comparison/re-bootstrap step; CMake is an alternative build path. This is stage0 + one self-rebuild, primarily for correctness of the produced `build.ninja`, not a fixed-point assertion.
- **Bazel.** `scripts/bootstrap/compile.sh` (current on master) compiles a bootstrap Bazel with shell + `javac` (excluding source files Bazel itself doesn't need), then Bazel builds Bazel (`bazel build //src:bazel`). The official *Compiling Bazel from Source* docs describe `bash ./compile.sh` producing a self-contained binary, and note reproducibility support via `SOURCE_DATE_EPOCH`. Bazel's CI (`.bazelci/presubmit.yml`) produces `//:bazel-distfile.zip` for bootstrapping and runs extensive integration tests (`src/test/shell/bazel/`), and Bazel's hermeticity + content-addressed caching is the real correctness mechanism. **Stage0 + self-build; reproducibility supported; no mandatory stage2==stage3 binary diff documented.**
- **Gradle -- the closest analogue.** `gradle/gradle`'s TeamCity config `.teamcity/src/main/kotlin/configurations/Gradleception.kt` (current on master) defines a build type **"Gradleception"** whose description is: *"Builds Gradle with the version of Gradle which is currently under development (twice)."* Its documented procedure (verbatim from the file):
  1. "Build a Gradle distribution with a fixed timestamp and hash it, but never use this distribution."
  2. "Build a Gradle distribution with this hash as a version + fixed timestamp -> dogfood-first"
  3. "Build a Gradle distribution using dogfood-first with this hash as a version + fixed timestamp different from the one above -> dogfood-second"
  4. "Use dogfood-second to run a Gradle build which runs tests."
  The steps use two fixed timestamps (`19800101010101+0000`, `19800202020202+0000`) and an MD5 over the first distribution as a version qualifier -- i.e., **deliberate reproducibility control** -- and the final `dogfood-second` (Gradle built by Gradle built by the wrapper Gradle) runs `clean sanityCheck test`. The stated rationale (from the code comments and the "dogfood" naming) is to validate that the in-development Gradle can build *and* run itself and its own build logic. This is effectively a **three-generation self-build** (wrapper Gradle -> dogfood-first -> dogfood-second), the deepest self-hosting chain of any mainstream build tool -- **but it is a functional/self-consistency test, not a bit-identical stage2-vs-stage3 diff.** The normal Gradle build uses the wrapper pointing at a released/nightly version plus included `build-logic` builds.
- **Apache Maven.** Today Maven is built with a **previous Maven release** (`apache/maven`; latest stable 3.9.16, released 17 May 2026, "the recommended version for all users" per the Maven download page; Maven 4.x is the current major line). Historically Maven 1.x bootstrapped via **Ant** (`build-bootstrap.xml`: "After initially constructing a basic Maven install with Ant, the bootstrap will use Maven to rebuild itself"), and Maven's docs stated "Maven uses itself to build itself!" The Ant bootstrap was **removed in Maven 3.5.0** (MNG-5904): "You can now only bootstrap Maven build with a previous version of Maven, but not with Ant anymore." So Maven does bootstrap-with-previous-release + uses `maven-integration-testing` to exercise the freshly built Maven, but there is no self-fixed-point compare. (Fedora's `javapackages-bootstrap` project separately provides a from-lower-level on-ramp for distro bootstrapping.)
- **Go's `go` command.** As above, the `go` build tool is bootstrapped *inside* the compiler's multi-stage process (`cmd/dist`: `go_bootstrap` is the temporary cmd/go built by toolchain1; toolchain2/3 follow). No comparison step in `cmd/dist`; reproducibility is verified separately.
- **Rust's build system.** The `bootstrap` crate (`x.py`, formerly rustbuild) is itself compiled by the stage0 rustc/cargo; Cargo is built by stage0 Cargo. Per the rustc-dev-guide, the build tool is just another stage0-built artifact; the fixed-point sanity check is on the *compiler/libraries* (stage2), not on the build tool.
- **Others (briefly):** **Please** (`thought-machine/please`): `./bootstrap.sh` "will set up the minimal environment needed to build Please, build it once manually and then rebuild it again using itself" (needs Go 1.11+) -- stage0 + self-rebuild. **Boost.Build/b2**: `bootstrap.sh` + `build.sh` (from-scratch engine build). **redo** (apenwarr): a `minimal/do` shell implementation bootstraps the real redo. **tup**: `bootstrap.sh`/`build.sh`. **Buck2**: built with Cargo (Rust), dogfooded but not multi-stage self-compared. **Meson/SCons/waf**: Python-interpreted -- no compilation self-hosting problem (N/A), though Meson<->Ninja creates its own bootstrap loop noted by the bootstrappable-builds community (mitigated because samurai, a C reimplementation of Ninja, exists). **Autoconf/Automake**: self-built via their own generated `configure`.

**Direct answer to sub-question (4).** No mainstream build tool performs a mandatory GCC-style bit-identical stage2-vs-stage3 compare. The closest genuine multi-stage self-bootstrap-with-verification is **Gradle's Gradleception**, which builds Gradle with a Gradle that was itself built by the wrapper Gradle (three generations), deliberately controls timestamps for reproducibility, and then runs the test suite with the doubly-self-built distribution. It verifies *functional* self-consistency and DSL/build-logic compatibility, not byte-identity. Genuine bit-identity fixed-point verification in this domain exists only in reproducible-builds tooling (Debian, Go >= 1.21 toolchains) and in full-source bootstrap chains (Guix, nixpkgs stdenv) -- which rebuild make and the whole environment from an auditable seed, a *supply-chain* goal rather than a self-consistency assertion.

## Direct Answers to the Four Sub-Questions

1. **The three-stage compiler bootstrap (summary).** Build the compiler's source with the host compiler (stage1), rebuild the same source with stage1 (stage2), rebuild again with stage2 (stage3), then verify stage2 and stage3 are **bit-identical**. Stages 2 and 3 must match because both are produced from identical source by functionally-equivalent self-built compilers; stage1 differs legitimately because a foreign compiler built it. The compare is a self-consistency/reproducibility check that catches miscompilation, undefined behaviour, and nondeterminism -- **not** correctness, and **not** the trusting-trust attack (which needs DDC + reproducible builds).

2. **Does it make sense for build tools?** Only partially. The chicken-and-egg (stage-0) purpose transfers strongly and is already solved almost everywhere. The performance and bit-identical fixed-point purposes largely do **not** transfer, because a build tool's binary is produced by an external compiler and its real "output" is an orchestration/build-plan, not object code. A GCC-style binary compare of a build tool mostly tests the compiler, not the tool.

3. **The sensible adaptation.** Keep a mandatory **stage0** (bootstrap-from-nothing) and **stage1** (tool built by stage0). Add an **optional stage2** whose value is (a) validating the tool can still interpret its own build DSL, and (b) a reproducibility/fixed-point check *at the build-plan/artifact level* (diff generated build files / command graphs / action graphs, or final artifacts for hermetic tools). Test incremental-rebuild correctness separately, since no bootstrap covers it.

4. **Has any known tool implemented something similar?** Yes -- **Gradle's "Gradleception"** is the closest, running a three-generation self-build with reproducibility controls and a test run, though it checks functional consistency, not byte-identity. Make, CMake, Ninja, and Bazel all implement the stage-0 self-host but stop there. True bit-identity fixed-point verification exists only in reproducible-builds efforts and full-source bootstrap chains (Guix, nixpkgs), which rebuild the whole toolchain -- make included -- from an auditable seed.

### Implicit assumptions in the question that the evidence challenges
- **"Bootstrap implies a trust guarantee."** It does not; self-bootstrap propagates a poisoned compiler perfectly. Trust needs DDC + reproducible builds.
- **"Three stages is the standard."** Only GCC mandates three with a compare; Rust does two, GHC's third is optional, Go builds three but never compares them.
- **"A build tool is one kind of thing."** It is at least three (executors, generators, integrated systems) plus a compiled-vs-interpreted-vs-JVM axis, and the analysis differs per category.
- **"'Bootstrap' means self-hosting."** In build-tool repos it very often means "regenerate configure" (autotools/gnulib), an unrelated operation.
- **"A build tool self-build would meaningfully verify the tool the way GCC's does."** For a compiled tool the bytes come from the external compiler, so a binary compare is mostly compiler-testing theatre; the meaningful check is at the build-plan/artifact level.

### Open points where evidence was thinner
- I did not exhaustively audit every tool's *entire* CI for hidden self-compare jobs; the survey reflects primary sources actually read (repository files and official docs). Buck2's and tup's internal CI self-testing were assessed only from their public bootstrap scripts/design docs.
- The exact "number of generations" in Gradleception depends on whether you count the throwaway hashing build (explicitly "never used").
- The `go.dev/doc/install/source` prose gives the general N-2-rounded-down-to-even rule but does not list a verbatim "go1.24.6" row; the patch-level pin appears in Go's issue tracker (#75143) and cmd/dist's build tag, consistent with the formula for Go 1.26.

---

## Caveats
- **The stage2/stage3 identity property vs. an actual compare are different things.** GCC actively diffs; GHC's stage3 is optional; **Go builds toolchain3 but does not diff it** (confirmed from current `cmd/dist/build.go`, Sept 2026). Do not assume "builds three stages" implies "compares them."
- **Gradleception is CI configuration, not a shipped end-user bootstrap.** It is current on `gradle/gradle` master as of this writing, but it is an internal correctness gate; the description and step names are quoted verbatim from `Gradleception.kt`.
- **"Bootstrap script" ambiguity** -- many repos contain a `bootstrap`/`autogen.sh` that only regenerates `configure`; do not mistake these for self-hosting bootstraps.
- **Version currency:** Bazel's older docs pin JDK 8 for bootstrap; the current docs (bazel.build/install/compile-source) require a newer JDK (JDK 25 in the latest instructions). Maven's latest stable is 3.9.16 (17 May 2026) with Maven 4.x as the current major line. Go's minimum bootstrap on main is go1.24.6.
- **Interpreted tools (Meson, SCons, waf) are out of scope for a compile-time self-host**, but Meson's dependence on Ninja creates a separate, real bootstrap loop that the community mitigates via samurai (a C Ninja clone).
